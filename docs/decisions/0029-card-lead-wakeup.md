# ADR-0029: 실행 중 카드의 총괄 질문

## 개정 (2026-11-08): 분배한 열린 대화로 전달

[ADR-0034](0034-lead-tabs.md)에 따라 카드 질문은 현재 선택한 탭이 아니라 해당 실행의 `lead.dispatch` 또는 `lead.followup`을 기록한 대화로 간다. 그 대화가 열려 있으면 탭 전환 뒤에도 실행기와 복구 감시가 같은 대상으로 전달한다. 닫힌 대화에서 온 질문은 버리고 경고를 남기며, 출처를 찾지 못하는 이전 실행만 현재 대화로 보낸다. 답변 직전에도 열린 상태와 실행 중지를 확인하고 기존 메시지 접수·중복 방지·읽기 전용 규칙은 유지한다.

## 기존 결정

총괄이 분배한 실행에서 카드가 `o msg send --question --to lead`로 질문하면 실행기는 팀 메시지 기록을 감시한다. 메시지가 없으면 모델을 호출하지 않는다. 현재 총괄 대화에 해당 실행의 분배 기록이 있고 대화가 비어 있을 때만 첫 메시지를 원자적으로 접수해 총괄을 호출한다. 카드는 `o msg wait`으로 답을 기다릴 수 있다. 답은 원 질문의 ID를 참조하며, 저장한 뒤에만 질문을 처리 완료로 기록한다. 같은 질문에 답이 이미 저장된 경우 중복 답을 보내지 않는다.

팀 메시지 기록에 잘못된 UTF-8, 불완전한 JSON 또는 필수 전달 상태가 빠진 메시지 이벤트가 있으면 조회와 전달·상태 변경을 중단한다. 기록은 보존하며 사람이 손상 구간을 확인해야 한다. 줄바꿈만 빠진 완전한 마지막 이벤트는 기존 기록으로 확인한다.

카드 입력은 `lead.worker` 이벤트로 구분하며 사용자 지시나 승인으로 취급하지 않는다. 총괄은 분배 당시 선택한 공급자·모델·노력·프로필의 카드 질문 전용 읽기 세션을 사용하며 일반 총괄이나 YOLO 세션을 잇지 않는다. 답변을 저장하고 질문을 처리 완료한 뒤에만 `lead.worker-session`에 세션, 설정, 처리한 질문 위치와 그때까지의 대화 해시를 기록한다. 이후 같은 대화에서 설정과 대화 해시가 일치하고 미완료 카드 턴이 없을 때만 재사용한다. 다른 총괄 턴의 메시지·계획·분배·상태 기록은 이후 질문에 참고 자료로 전달하며, 길이 제한으로 빠진 내용이나 재사용 불가는 답변에도 표시하고 추측하지 않도록 한다. 대화 파일이 손상되거나 알 수 없는 기록이 있으면 질문 접수 전에 거부한다. 출력의 계획·설계·후속 지시는 자동 해석하거나 실행하지 않는다. 사용자 주석은 소비하지 않는다. 구독 로그인과 API 키 제거 규칙은 기존 총괄과 같다.

새 세션의 ID를 받지 못하면 답변을 전달하되 다음 질문에 재사용하지 않는다고 알린다. 일반 총괄 세션과 충돌하거나 재개한 세션의 ID가 일치하지 않으면 답변을 전달하지 않는다. 공급자가 재개를 거부하거나 중단되면 질문은 기존처럼 불명으로 남고 자동 재전송하지 않는다. Codex CLI 0.166.0 이상에서는 기본 모델로 선택한 세션도 재사용한다. 같은 app-server 연결에서 모델 턴이 없는 임시 스레드로 현재 모델·공급자를 확인하고, 그 모델을 지정해 재개한 응답이 일치할 때만 질문을 전달한다. 확인에 실패하면 질문을 자동 재전송하지 않는다. 이전 버전과 다른 공급자의 기본 모델은 매번 새 세션을 사용한다.

2026-11-04 실제 Codex 구독에서 기본 모델을 사용한 카드 질문 두 번이 같은 세션으로 이어졌고, 두 번째 질문은 신규 입력 6,023토큰과 캐시 입력 24,960토큰을 보고했다. 별도 실험에서 기본 모델을 바꾼 뒤 명시적으로 재개하면 이전 내용을 기억했으며, 같은 모델의 다음 턴에서 입력 40,151토큰 중 39,936토큰이 캐시로 보고됐다. 실측은 공급자의 캐시 유지나 비율을 보장하지 않는다. Claude의 실제 재개·캐시는 확인하지 않았다.

사람의 판단이나 권한이 필요한 카드는 `o msg send --approval --id <재시도키> "내용"`으로 명시한다. 이 요청은 총괄을 자동 호출하지 않고 팀 대화와 할 일에 승인 요청으로 남는다. 사용자는 팀 대화의 입력란이나 `o msg send --run <실행> --to <카드> --reply-to <요청ID> "답변"`으로 직접 답한다. 데스크톱과 개발 서버는 같은 요청 ID에 답하고, 답변을 저장한 뒤 요청을 처리 완료로 기록한다. 저장 후 상태 기록에 실패하면 그 사실을 알리며 같은 내용의 재시도는 중복 답변을 만들지 않는다. 표식이 있는 에이전트의 승인 답변은 CLI가 거부한다. 메시지 종류는 작성자가 지정하므로 일반 질문으로 잘못 표시된 승인 요청까지 확실히 자동 판별하지는 못한다. 팀 대화는 CLI 도구 권한 자체를 부여하지 않는다.

처리 중 다른 총괄 턴이 있으면 대기하며, 새 대화로 바뀌거나 실행이 중지되면 답을 전달하지 않는다. 접수 후 실패·중단은 불명 상태로 남겨 자동 재전송하지 않는다. 긴 답은 전체 정책 검사를 거쳐 실행의 `lead-results`에 원문을 저장하고 질문한 카드에 SHA-256 참조를 보낸다. 카드는 `o context --lead-result <질문ID> <해시> <위치>`로 원문 전체를 UTF-8 경계에 맞춰 읽으며, 매번 해시와 해당 질문·수신자를 검증한다. 원문은 임시 파일을 동기화한 뒤 새 이름에 연결하여 불완전한 파일을 완료된 결과로 노출하지 않는다. 해당 컨텍스트 명령을 지원하지 않는 프로바이더는 참조를 받지 않고 불명 상태로 남는다. `o lead retry <실행ID> <메시지ID>` 또는 팀 대화의 상태 복구는 먼저 기존 답변을 확인한다. 이미 답이 저장됐으면 처리 완료만 기록하고, 답이 없으면 사용자의 명시적 조작으로 다시 대기시킨다. 총괄이 응답 중인 경우에는 복구하지 않는다. 대기 중인 메시지는 `o lead wake <실행ID>` 또는 팀 대화의 전달 버튼으로 처리할 수 있다.

결과 조회는 실행 기록 잠금을 잡아 다른 카드가 기록 중인 미완성 줄을 읽지 않는다. 총괄의 원시 출력 파일을 열거나 쓰지 못하면 대화에 불완전 기록을 알리되 정상 수신한 답변은 보존한다. 표준 출력을 끝까지 읽지 못한 경우에는 완성된 답변으로 처리하지 않는다.

실행기와 앱은 각각 대기 메시지를 감시한다. 앱이나 개발 서버를 다시 열면 종료·중지 기록이 없는 실행의 대기 메시지를 다시 확인한다. 실행기와 앱이 동시에 확인하더라도 총괄 턴 잠금과 메시지 접수 상태로 중복 호출을 막고, 이미 접수됐거나 불명인 전달은 자동 재전송하지 않는다. 실행이 끝난 뒤 남은 질문은 수동 전달한다. 앱과 개발 서버가 모두 닫혀 있고 실행기도 중단된 동안에는 감시하지 않는다. 빠른 카드가 분배 기록보다 먼저 종료되면 실행기는 최대 2초 동안 기록을 기다린다. 기록과 잠금은 같은 OS 사용자에 대한 보안 격리가 아니며, 공급자의 실제 CLI·구독 캐시 동작과 프로그램 종료 상황은 별도 실측이 필요하다.
