# ADR-0049: 승인한 실행 입력을 부모에서 자식으로 직접 전달

- 상태: 채택 (플랫폼별 검증 및 남은 경계는 아래 참조)
- 날짜: 2026-11-12
- 관련: ADR-0008, ADR-0013, ADR-0042, ADR-0043, ADR-0046
- 근거: statefs F3/F6, 대표 지시의 승인 계획·모드 불변 전달

## 배경

부모가 검사한 계획을 저장한 뒤 자식이 `plan.json`, `clean`, `yolo`, `no-context`, `scheduled`, `isolated-worktrees`를 다시 읽었다. 검사와 실행 사이에 파일을 바꾸면 실제 작업 또는 실행 권한이 달라질 수 있었다. 파일 옆에 해시나 서명을 저장하는 것만으로 그 파일의 승인 출처를 증명할 수는 없다. 화면도 계획 ID만 전달해 사용자가 보고 있던 계획과 서버가 실행하는 계획의 일치를 보장하지 못했다.

## 결정

1. 부모는 정책 검사를 통과한 `Plan`, `RunMode(profile/context/yolo)`, 예약 여부, 분리 작업 폴더 여부, 후속 실행 정보를 `RunInput` 하나로 보관한다. 파일에는 기존 형식의 기록을 계속 남기되 실행 입력으로 다시 읽지 않는다. 자식의 정책 재검사도 같은 값을 사용한다. 예산·서비스 한도·중지·작업 폴더 안전 검사는 실행 시점의 조건을 계속 확인한다.
2. 같은 실행 파일의 부모가 만든 비공개 표준 입력 연결로 JSON을 전달한다. Windows는 익명 파이프 서버 PID와 실행 파일 경로를, Linux는 Unix 소켓 `SO_PEERCRED`와 `/proc/<pid>/exe`를, macOS는 `LOCAL_PEERPID`와 `proc_pidpath`를 확인한다. 실행 파일 이름만 같은 다른 경로는 허용하지 않는다. Windows API의 근거는 [GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid), Unix 구현의 근거는 [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)와 [Apple의 LOCAL_PEERPID 구현](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_usrreq.c)이다.
3. 입력은 최대 4 MiB이며 ID·상태 폴더·후속 실행 종류를 확인한다. 예약 실행과 YOLO의 조합은 거부한다. 자식의 수신 확인을 최대 15초 기다려 부모의 신원을 확인할 동안 부모를 유지한다. Unix는 쓰기 방향만 닫고 응답까지 연결 자체를 유지한다. 전달 실패·시간 초과에는 시작한 자식을 종료하고 오류를 돌려준다.
4. `_run`, `_followup`, `_review`도 이 입력 없이는 실행하지 않는다. 새 호출자는 `_run-approved`, `_followup-approved`, `_review-approved`를 사용해 옛 바이너리가 파일 기반 실행으로 오인하지 못하게 한다. CLI는 자신을, Tauri는 앱 실행 파일 자신을 자식으로 띄운다. 앱 자식은 창·단일 실행 플러그인 초기화 전에 내부 실행을 처리한다. 개발 서버는 `approved-run-input-v1` capability를 요구한다.
5. 화면에서 받은 원래 계획 전체를 `expectedPlan`으로 전달한다. core는 대화 잠금 안에서 현재 계획과 값이 같은지 확인한다. 계획의 프로젝트를 대화 메타데이터로 덮어쓰지 않고 서로 다른 프로젝트면 거부한다. 화면의 프로필과 YOLO 상태도 명시하며, 현재 YOLO 설정과 다르면 재확인을 요구한다. 모드 조회 중·실패 시 실행 버튼은 비활성화한다.
6. 직접 CLI 실행은 사람이 지정한 계획을 검사한 값으로 시작한다. 자동·예약 분배도 부모가 이미 검사한 계획을 전달한다. PR 검토 입력은 생성할 때 공유 컨텍스트를 끈다. 후속 작업은 승인 시 조상 계획·프로필·격리·참조를 잡고, 끝난 작업의 세션과 폴더도 함께 잡는다. 대기 중인 후속 작업은 기존 중지·순서·동시 실행 제한을 유지하며 앞선 실행의 최종 이벤트를 기다린다.

## 호환성과 한계

- 기존 계획·모드 표식·이벤트의 형식과 조회는 유지한다. 이전 기록은 읽을 수 있으나 디스크의 실행 폴더만으로 내부 실행기를 다시 시작하는 방식은 더 이상 지원하지 않는다. 종료·복구는 기존 이벤트와 프로세스 상태를 계속 사용한다.
- 시작 콜백은 `Fn(&str, &RunInput) -> io::Result<()>`, 실행기는 `run_detached(&RunInput)`을 받는다. 코어의 간단한 `run_plan*` 래퍼는 명시된 프로필의 일반 모드·공유 컨텍스트·격리 없음으로 실행한다. 다른 모드가 필요한 호출자는 `run_input`을 쓴다.
- 부모 프로세스·실행 파일·상속 핸들을 공격자가 장악한 경우까지 인증하는 구조는 아니다. OS 에이전트 격리와 상태 폴더 접근권은 별도 작업이다. 특히 대기한 원본 실행의 세션·완료·전환 이벤트, 예산·중지 등 실행 중 변하는 상태는 이 입력의 불변성 보장에 포함하지 않는다. 그 상태를 공격자가 수정할 수 없는지는 별도로 강제해야 한다.
- 승인 전 저장된 계획 자체를 신뢰 가능한 제안으로 만드는 문제도 별도다. 이 변경은 화면에서 검토한 값과 부모가 검사해 전달한 값, 실제 실행 입력의 연결을 보장한다.
- Windows 실제 프로세스·파이프와 가짜 프로바이더로 회귀 검증했다. Linux·macOS 실행 및 설치 앱의 실제 Tauri 자식 실행은 아직 검증하지 않았다. [검증 보고서](../reports/2026-11-12-execution-integrity.md)를 따른다.
