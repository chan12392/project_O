# ADR-0032: 전체 총괄 — 프로젝트 총괄 위에서 전체를 보고 일을 넘긴다

- 상태: 채택 (단계적으로 구현)
- 날짜: 2026-11-07
- 별도 승인 대기 없음 (ADR-0012)
- 관련: [ADR-0008](0008-lead-chat.md)(총괄 채팅), [ADR-0014](0014-yolo-mode.md)(YOLO), [ADR-0018](0018-lead-work-graph.md)(설계 패널과 작업 그래프), [ADR-0019](0019-navigation-images-schedules.md)(왼쪽은 전체, 오른쪽은 현재 프로젝트), [ADR-0022](0022-agent-session-continuations.md)(후속 지시)

## 개정 (2026-11-08): 전체 총괄도 여러 탭

[ADR-0034](0034-lead-tabs.md)에 따라 전체 총괄도 프로젝트 루트에 여러 탭을 열 수 있으며 모두 읽기 전용이고 writer는 없다. 전체 현황은 길이 상한 안에서 프로젝트별 열린 대화 수와 현재 탭의 요청·답·계획·실행을 요약한다. 요청을 만든 탭이 열려 있으면 선택한 탭이 바뀌어도 전달할 수 있다. 전달 턴 시작 전에 목적지 탭을 정해 유지하며, 목적지가 닫혔거나 원본 요청이 중지되면 전달하지 않는다. 대상이 바쁘면 기존처럼 거절한다. 실제 `lead.forward` 이벤트에는 아래 초안의 `threadId?`가 없으며, 목적지는 전달을 시작할 때 선택한다.

## 배경

- 총괄은 프로젝트마다 하나다(`leads/current.json`: 프로젝트 → 현재 대화). 여러 프로젝트를 돌리면 사람이 프로젝트를 하나씩 열어 상태를 확인하고, 어느 프로젝트 총괄에게 무엇을 시킬지 직접 골라야 한다.
- 대표 요청: 프로젝트별 총괄은 그대로 두고, 그 위에 전체 프로젝트를 관리하는 총괄을 둔다. 사람은 가장 중요한 결정만 한다.
- 무엇이 "중요한 결정"인지를 LLM이 매번 판단하게 하면 흔들린다. 판단은 코드 규칙으로 고정한다.

## 결정

```
사람 ──▶ 전체 총괄 (읽기 전용 · 전체 현황) ──o-forward──▶ 프로젝트 총괄 (읽기 전용 · 계획 제안)
                                                                   │ o-plan
                                                     사람 "실행" (또는 YOLO 자동 실행 한도) ──▶ 카드
```

- **전체 총괄은 하나다.** 프로젝트 루트 폴더(`projects::list`의 `root`, 기본 `~/.project_o/project`, 설정에서 바꿀 수 있음)를 프로젝트로 하는 총괄 대화가 전체 총괄이다. 루트 자체는 프로젝트로 등록할 수 없으므로(`projects::add`가 거부) 기존 프로젝트 대화와 겹치지 않는다. 대화 저장·턴 잠금·승인·중지·새 대화는 프로젝트 총괄과 같은 코드를 쓴다.
- **할 수 있는 일:** 모든 프로젝트의 현황(현재 대화의 마지막 요청·답, 실행하지 않은 최신 계획, 기다리는 질문·승인, 최근 실행 상태)을 O가 프롬프트에 넣어 주고, 전체 총괄은 그것을 보고 답한다. 일을 시킬 때는 ```` ```o-forward ```` 블록으로 프로젝트 총괄에게 요청을 넘긴다.
  - 형식: `[{"project":"등록된 프로젝트 경로","text":"프로젝트 총괄에게 보낼 요청"}]`
- **할 수 없는 일:** 카드 계획(`o-plan`)과 후속 지시(`o-followup`)를 직접 내지 않는다. 섞여 있으면 아무것도 보내지 않고 오류로 남긴다. 카드 분배는 언제나 프로젝트 총괄의 계획을 거친다.
- **사람이 하는 결정은 지금과 같다:** 카드 실행(프로젝트 화면의 "실행", 또는 YOLO가 켜졌을 때의 자동 실행 한도 — ADR-0014). 요청 전달 자체는 사람 승인 없이 자동이다. 프로젝트 총괄은 읽기 전용(일반 모드)이고 계획을 제안만 하므로, 전달만으로는 아무것도 실행되지 않는다.
- **코드가 고정하는 한도** (`lead::overall`):
  - 한 턴에 넘길 수 있는 요청은 3개, 한 프로젝트에 하나씩이다.
  - 넘길 곳은 지금 목록(`projects::list`)에 있는 프로젝트뿐이다. 루트 자신, 목록에 없는 경로, 없어진 폴더는 거부한다.
  - 요청 글은 카드 작업과 같은 길이 상한(`LIMITS.max_task_chars`)을 지킨다.
  - 프로젝트 총괄이 답하는 중이면 그 프로젝트로는 넘기지 않고 오류로 남긴다(기다렸다 보내지 않는다).
  - 턴이 끝난 상태가 불명이거나, 중지됐거나, "새 대화"로 바뀌었으면 보내지 않는다.
- **넘겨받은 요청은 출처를 단다.** 프로젝트 대화에 사람의 메시지와 구분되는 `lead.user`(`origin: "overall"`)로 남고, 프롬프트에는 "[전체 총괄이 넘긴 요청]"으로 들어간다. 화면도 사람이 쓴 글과 다르게 보여 준다.
- **전달은 백그라운드로 한다.** 전체 총괄 턴이 끝나면 O가 `o _lead-forward <전체 대화 id> <번호>`를 띄운다. 이 명령은 요청 글을 명령줄로 받지 않고 O 상태 폴더의 전체 대화 기록(`lead.forward`)에서 읽어, 전체 총괄과 같은 에이전트·모델·프로필로 프로젝트 총괄에게 보낸다.
- **화면:** 왼쪽 사이드바 맨 위에 "전체 총괄"을 둔다. 누르면 가운데에 전체 총괄 대화가 나오고, 넘긴 요청마다 해당 프로젝트 대화로 가는 링크가 붙는다.

## 이유

- 새 저장 형식이나 새 프로세스 모델 없이 기존 총괄 대화를 그대로 쓴다. 다른 점은 프롬프트(전체 현황)와 답의 블록(`o-forward`)뿐이라 검사·잠금·복구 경로를 다시 만들지 않는다.
- "무엇을 사람에게 물을지"를 LLM에 맡기지 않는다. 실행 권한은 지금처럼 프로젝트 쪽 계획 승인에만 있고, 전달은 실행이 아니므로 자동으로 둔다.
- 전체 총괄이 카드를 직접 나누면 프로젝트 간 선후 관계·충돌을 새로 검사해야 한다. 이번 범위에서는 하지 않는다.

## 영향과 한계

- `LeadEvent`에 `lead.forward { project, text, threadId?, provider, model?, effort?, profile }`가 생기고, `lead.user`에 선택 필드 `origin`이 생긴다. 예전 빌드는 모르는 줄을 건너뛰고, `origin` 없는 `lead.user`는 사람의 글이다.
- 전체 총괄의 읽기 범위는 프로젝트 루트다. 루트 밖에 등록한 프로젝트는 O가 넣어 준 현황으로만 본다.
- 전체 총괄이 읽은 프로젝트 파일에 지시가 섞여 있으면 그것이 요청 글로 넘어갈 수 있다. 프로젝트 총괄은 그 글을 사람의 지시가 아닌 "전체 총괄이 넘긴 요청"으로 받고, 실행은 여전히 사람(또는 YOLO 한도)이 정한다. YOLO가 켜져 있으면 넘긴 요청에서 나온 계획도 자동 실행 한도 안에서 실행될 수 있다.
- 예약(ADR-0019)과 카드의 총괄 질문(ADR-0028)은 프로젝트 총괄에만 둔다.

## 단계

1. core·CLI: `lead::overall`(루트 판별, 전체 현황, `o-forward` 해석·검사), 턴 처리, `o _lead-forward`, `lead.user` 출처. `o lead send --overall`.
2. 앱: 사이드바 "전체 총괄", 대화 화면, 넘긴 요청의 링크, 넘겨받은 요청 표시. 개발 서버 `/api`에도 같은 동작.
3. 실제 경로 확인: 두 프로젝트에 요청을 넘기고 → 각 프로젝트 계획 → 사람이 실행 → 전체 총괄이 다음 턴에 결과를 보고한다. 바쁜 프로젝트, 목록에 없는 경로, 4개 이상의 요청, `o-plan`이 섞인 답도 확인한다.
