# ADR-0025: 병렬 작업의 결과 보존과 인계 (부분 구현)

상태: 부분 구현. 격리된 작업 인계와 자원 선언·예약은 구현되었고 종료 불명 예약의 복구 도구는 남았다.

일반 `o dispatch`도 총괄 분배와 같이 실행 전에 프로젝트를 검사하고 카드마다 별도 작업 폴더를 만든다. Git 프로젝트의 미커밋 변경은 보존하며 분배를 거부한다. 결과는 각 카드의 작업 폴더에 남고 원본에 자동 적용하지 않는다. CLI 응답의 `isolated`와 `o status <runId>`의 `작업 폴더`에서 분리 여부와 위치를 확인한다.

새로 분리한 실행의 `o status`는 작업 전 Git 커밋 또는 비 Git 기준 복사본 경로도 표시한다. 비 Git 기준은 생성 시 파일 내용·파일 권한·경로의 해시를 저장하고 조회 시 비교한다. 기록 자체를 바꾸는 같은 사용자에 대한 보안 보증은 아니다. 해시가 없는 예전 실행은 직접 비교해야 한다. 원본에 안전하게 변경을 적용하는 기능은 아직 없다.

`o changes <runId> <cardId>`는 해당 카드의 읽기 전용 변경 목록을 JSON으로 보여 준다. 후속 작업은 `baselineRunId`로 표시된 최초 실행의 기준부터 누적 변경을 보여 준다. Git은 기준 대비 변경과 스테이징·작업 파일·미추적·무시 파일을 나눠 표시하고, 변경이 숨겨질 수 있는 assume-unchanged·skip-worktree 파일은 `masked`에 별도 표시한다. 이 파일의 실제 변경 여부는 따로 확인해야 한다. 비 Git은 기준 복사본과 파일 내용·권한을 비교하며 기준 해시가 없거나 불일치하면 비교를 거부한다. 실행 중에도 조회할 수 있으므로 목록은 그 시점의 참고 정보이며, 안전한 원본 적용을 보증하지 않는다. 카드에서는 다른 실행의 파일 목록 접근을 막는다.

선행 카드의 결과는 참고 데이터이며 후속 카드의 권한이나 지시가 아니다. 실행기는 결과를 1,000자에서 자르지 않고, JSON 결과가 12,000바이트 이하면 전체를 전달한다. 더 크고 `o context`를 쓸 수 있는 카드에는 실행·선행 카드·크기·SHA-256과 읽기 명령을 전달한다. `o context --result <선행 카드> <해시> <위치>`는 해당 실행 계획의 직접 선행 결과만 읽고 매번 전체 해시를 확인한 뒤 최대 4,096바이트의 UTF-8 경계 조각과 다음 위치를 반환한다. 기록 손상·완료 상태 변경·해시 불일치·잘못된 위치는 오류다. 원문은 실행 이벤트에 그대로 남으며 도구 접근이 불가능하거나 결과를 확인하지 못하면 후속 카드에 중단을 지시한다. CLI 셸 명령이 허용되지 않은 Devin은 큰 결과를 부분 전달하지 않고 후속 시작을 거부한다. 실행기의 사전 확인은 OS 접근만 확인하며 각 프로바이더의 실제 샌드박스에서 읽히는지 보장하지 않는다.

결과 조회는 줄 단위 기록이 완성됐는지 확인한다. 선행 카드의 성공 뒤 재시작·재대기가 기록되면 이전 결과를 더 이상 읽지 않으며, 총괄 답변은 질문 뒤에 해당 카드로 전달된 기록이 있어야 한다.

긴 총괄 답변의 저장·조회는 실행 및 결과 폴더의 링크를 거부하고, 하드 링크된 결과 파일을 읽지 않는다. Windows에서는 처리 중 폴더 이동과 파일의 쓰기·삭제를 막는다. 비 Windows에서 경로 검사와 접근 사이의 모든 경합을 차단하지는 못한다.

카드의 표준 출력은 바이트 그대로 기록한다. 표준 출력 또는 오류 로그의 기록 실패는 카드 실패로 취급하며, 실행 도중 오류가 생기면 프로세스 종료를 시도한다. 프로세스가 살아 있는 것으로 확인되면 슬롯과 활성 표시를 되돌리지 않고, 종료 이벤트가 있더라도 해당 카드의 세션을 이어서 사용하지 않는다.

실제 카드 종료 기록이 없는 중단된 후속 실행은 화면에 실패로 표시하더라도 세션 재사용을 거부한다. 화면용으로 합성한 실패 이벤트는 프로세스 종료의 증거가 아니다.

Git 분리 작업에서 후속 카드는 선행 카드의 커밋과 작업 파일 변경을 기준 커밋과 비교해 자기 폴더에 적용한다. 임시 인덱스를 쓰므로 선행 카드의 실제 인덱스는 변경하지 않으며 추가·삭제·바이너리를 포함하고 패치와 적용 전 파일을 실행 기록에 보존한다. 같은 파일에 스테이징된 내용과 다른 작업 파일이 함께 있으면 어느 쪽도 버리지 않고 중단한다. 원본 기준 변경, 범위 밖 변경, 무시 파일, 링크·서브모듈 변경, 후속 폴더의 사람 변경, 패치 충돌이나 원본과 다른 적용 바이트를 발견하면 후속 카드를 시작하지 않는다. Git의 개행 변환 때문에 바이트가 달라지는 경우도 현재는 거부한다.

Git 선행 변경을 수집할 때 현재 추적·미추적 일반 파일의 하드 링크도 거부한다. Windows에서는 수집 중 해당 파일 핸들을 열어 쓰기·삭제를 막으며, 열린 파일 수가 너무 많거나 다른 프로세스가 쓰는 중이면 안전하게 중단할 수 있다. 확인 뒤 새로 생기는 파일이나 상위 경로 교체까지 원자적으로 차단하지는 않는다.

비 Git 복사본은 최초 원본의 파일 바이트와 권한을 기준으로 선행 복사본의 추가·수정·삭제를 후속 복사본에 인계한다. 원본과 기준 사본, 후속 복사본이 기준과 다른 경우 또는 선행 복사본의 링크·중첩 저장소나 Git 메타데이터 변경이 발견되면 시작하지 않는다. 여러 선행 작업이 같은 경로나 상하위 경로를 바꾼 경우에도 자동 병합하지 않는다. 적용 전 기존 파일은 후속 복사본 옆의 `handoff-<카드 순번>` 폴더로 옮겨 보존하며, 실패한 복사본도 검토를 위해 남긴다. 디렉터리 권한 변경은 인계 대상이 아니다.

Windows와 Unix의 비 Git 복사와 비교는 일반 파일 핸들의 하드 링크 수를 확인하고 링크 수가 1이 아니면 거부한다. Windows에서는 파일을 읽는 동안 쓰기·삭제 공유를 허용하지 않는다. 이 검사는 작업 폴더의 상위 디렉터리를 동시에 교체하는 모든 경합을 차단하지 않는다.

복사본 확인과 적용 사이에 같은 OS 사용자의 동시 수정이나 링크 교체를 원자적으로 막지는 못한다. 작업공간 분리는 외부 자원의 OS 격리를 뜻하지 않는다.

## 공용 자원 계약

- 계획 카드의 `resources`는 `kind` (`project-path` 또는 `external`), `key`, `mode` (`read` 또는 `write`) 목록이다. `project-path`는 프로젝트 상대 경로를 기존 부모까지 정규화하고 링크를 해석하며 프로젝트 밖 경로를 거부한다. 같은 경로와 상하위 경로는 겹치며 읽기끼리만 병행한다. 외부 키는 앞뒤 공백 제거와 소문자 변환 후 비교한다. 생략하거나 빈 배열이면 모든 자원을 독점한다. 명시한 목록이 완전한지 O는 알 수 없으므로 불확실하면 생략해야 한다.
- 실행기들은 SQLite 쓰기 트랜잭션 하나에서 기존 자원 예약, 동시 상한, 하루 상한을 확인하고 슬롯과 자원을 함께 예약한다. 충돌하면 대기한다. 이전 버전의 활성 슬롯처럼 범위가 불명인 실행은 전체 자원과 충돌한다.
- 자원 예약은 실행기가 죽어도 자동 삭제하지 않는다. Windows에서는 프로세스를 일시 정지 상태로 시작해 잡 객체에 넣은 후 재개하고, 프로세스 종료와 잡 객체의 모든 프로세스 종료를 확인한 뒤에만 해제한다. 자식이 출력 파이프를 계속 잡고 있으면 실행 종료와 예약 해제가 지연될 수 있다. 잡 객체를 만들지 못하거나 종료를 확인하지 못한 경우, 실행기 중단 또는 비 Windows 환경에서는 예약이 남을 수 있으며 충돌 작업과 해당 세션 재개가 차단된다. Linux에서는 시작 전 예약 등 종료 근거가 이미 기록된 경우 소유 프로세스의 종료를 확인해 복구할 수 있다. 작업 프로세스 트리의 종료를 확인하는 기능은 아직 없다.
- `o resources --json`, 앱의 자원 예약 점검과 개발 서버는 예약별 실행기·작업 PID 및 기록된 생성 시각을 보여 준다. 새 예약은 프로세스 생성 직전에 시작 시도 표식을, 프로세스 트리 종료를 확인한 뒤 예약 해제 전에 종료 확인 표식을 영속 기록한다. 시작 전이거나 종료 확인 표식이 있는 예약은 `o resources recover <예약 ID>` 또는 앱의 복구 확인으로 Windows에서 동일 소유자의 종료를 확인한 후 원자적으로 해제한다. 이미 시작한 작업은 하루 시작 횟수를 되돌리지 않는다. PID가 재사용된 경우 생성 시각으로 구분하며 살아 있거나 확인할 수 없는 소유자는 거부한다. 종료 확인 전에 중단됐거나 증거가 없는 기존 예약은 종료 불명으로 남는다. 비 Windows의 정상 종료 확인과 복구는 아직 지원하지 않는다.
- 비 Windows에서 직접 시작한 프로세스의 종료는 남은 자손의 종료를 증명하지 않는다. POSIX 프로세스 그룹도 자손의 그룹 이탈을 막지 못하므로 단독으로 예약 해제 근거가 될 수 없다. Linux의 cgroup 등으로 지원할 때에는 자손이 격리 밖으로 이동할 수 없는 조건과 격리 단위 전체의 종료를 실제 환경에서 확인해야 하며, 이를 증명하지 못하면 예약을 유지한다. macOS 등 다른 플랫폼에도 별도의 종료 증명이 필요하다.
- 중지는 실행 폴더에 요청을 기록하고 살아 있는 Windows 실행기가 보유한 잡 핸들로 처리한다. 구형 표식이나 실행기가 없는 예약의 PID는 종료하지 않으며 예약은 증거가 확보될 때까지 남는다. 비 Windows에서는 중지 요청이 기록되지만 실행 중인 작업을 즉시 종료하는 격리 핸들이 없어 자연 종료를 기다릴 수 있다.
- 총괄도 오래된 실행 표식의 PID만으로 프로세스를 종료하거나 표식을 삭제하지 않는다. 소유자가 사라졌거나 종료 증명이 없는 표식은 종료 불명으로 표시하고 같은 프로젝트의 새 총괄을 막는다. Windows의 새 총괄은 시작 전 잡에 넣고 전체 종료를 확인한다. 비 Windows는 이 확인이 없어 정상 종료 후에도 불명으로 남을 수 있으며 안전한 복구 경로는 아직 없다.
- 선언은 에이전트 접근을 제한하거나 누락을 탐지하지 않는다. 같은 OS 사용자의 기록 변경, 작업 중 링크 교체, 하드 링크와 파일시스템별 별칭, 외부 서비스의 비동기 작업까지 격리하지 못한다. 이전 버전의 실행기와 새 실행기를 혼용하면 이전 실행기의 예약은 자원 계약을 따르지 않는다.
- 카드에 `o msg send --question`으로 질문하면 마지막 기록상 대상이 대기·종료·불명인 경우 발신자에게 대기 위험을 알린다. 이 상태는 조회 시점의 기록이며 이후 시작이나 답변을 보장하지 않는다. 카드에는 자원을 점유한 채 무기한 기다리지 말고 총괄에 막힌 점을 알리도록 안내한다.
- 결과 조각의 읽기 권한과 모델이 실제 끝까지 읽는지는 각 프로바이더의 공식 CLI에서 추가 검증해야 한다. 같은 OS 사용자가 환경이나 기록을 고칠 수 있으므로 카드 신원은 강제 격리 경계가 아니다.

총괄에는 짧은 실행 미리보기와 생략 수, 실행·카드 ID로 검색할 수 있는 줄 단위 색인을 보낸다. 색인은 필요한 실행 상태·결과 이벤트의 원문 페이지를 가리키며 작은 JSON 문자열을 순서대로 이어 붙이면 원문 그대로다. 해석 가능한 미지 이벤트는 보존하고 손상된 기록은 불명으로 알린다. 전체 도구 로그는 포함하지 않으며 카드 내용은 사용자 지시가 아닌 비신뢰 자료다. Claude의 기존 읽기 전용 첨부 폴더 권한을 쓰고 셸 권한은 추가하지 않는다. 기록을 안전하게 읽거나 파일을 만들 수 없을 때는 사유를 사용자와 총괄에 알리고, 총괄 대화는 계속하되 결과를 추측하지 않도록 한다. 비 Windows의 안전한 원문 파일 처리는 미지원이며 실제 공급자 CLI 샌드박스의 읽기 동작은 별도 확인이 필요하다.

Windows에서는 원본 파일의 링크·하드 링크를 확인하고 파일을 읽거나 전달하는 동안 핸들을 유지해 덮어쓰기와 경로 교체를 막는다. 새 결과는 매번 임시 파일로 만들며 이전 버전이 남긴 결과 파일은 자동 정리하지 않는다. 전달 도중 새 하드 링크를 만드는 것은 막지 않지만 그 링크를 통한 쓰기도 핸들을 놓기 전에는 거부한다. 로컬 임시 폴더 실험에서는 하위 폴더 핸들만 있어도 상위 폴더 이동이 거부됐지만 다른 파일시스템에도 이를 보장할 근거가 없어 드라이브 루트부터 조상 핸들을 유지한다. 이 동안 사용자 조상 폴더의 이동·이름 변경이 차단될 수 있으며, 안전한 경로 고정과 이동 허용을 함께 검증하기 전까지 범위를 줄이지 않는다.

총괄 실행 요약과 원문 색인은 모든 크기의 기록을 같은 스트리밍 경로로 처리한다. 원본은 실행당 파일 핸들과 조상 핸들로 고정하고, 정해진 크기의 버퍼로 행 경계를 찾은 뒤 필요한 이벤트만 UTF-8 최대 256바이트씩 JSON 문자열 한 줄로 쓴 임시 페이지 파일과 색인 파일에 저장한다. 색인에는 이벤트별 시작 줄·줄 수·SHA-256을 기록하며 페이지를 다시 읽어 해시를 검증한 후 총괄에 전달한다. 총괄은 Read의 offset·limit으로 필요한 줄만 읽어 JSON 문자열을 이어 붙인다. 파일 두 개는 총괄 실행 중 고정되고 종료나 오류 시 닫힌다. 이전 버전이 남긴 결과 파일의 총량 제한이나 자동 정리는 없다.

한 요청의 입력은 합계 128 MiB, 페이지 출력은 256 MiB, 실행은 128개, 색인 항목은 512개, JSON 중첩은 128단계까지다. 256 KiB 이하 이벤트는 한 항목씩 파싱하고 상태 요약을 위해 최대 1 MiB의 이벤트만 보관한다. 이 한도를 넘으면 상태를 불명으로 알린다. 256 KiB를 넘는 이벤트는 O가 기록하는 필드 순서와 형식의 `card.end`만 원문을 제공하며, 그 외의 대형 이벤트와 해석할 수 없는 손상된 행은 제공하지 않고 불명으로 표시한다. `msg`, `msg.state`, `card.tool`, `card.message`, `card.input`은 제공하지 않는다. 원본이 열려 있는 동안 쓰기·경로 교체를 막고 크기와 페이지 해시를 확인한다. 작은 미완성 행이 유효한 JSON이면 원문을 불명으로 제공하고, 큰 미완성 행은 해당 실행을 불명으로 남기며 다른 실행의 정상 원문은 유지한다. 이 상태 확인 불가는 `lead.warning`으로 대화와 CLI에 표시하며 총괄 응답 자체의 성공·실패와 구분한다.

Windows의 사람용 `o lead log-page --project <폴더> <runId> - 0`은 현재 대화에서 분배한 실행의 완료 이벤트가 마지막인 원본 로그를 최대 4,096바이트씩 읽는다. 응답의 SHA-256과 nextOffset을 다음 호출에 주면 매번 전체 파일을 고정하고 다시 해시해 변경을 감지한다. 매 페이지에 전체 로그를 다시 해시하므로 큰 기록을 끝까지 읽는 데 드는 시간과 디스크 읽기량이 크다. 원본 로그 전체에는 도구·팀 기록이 포함될 수 있어 에이전트 실행 환경에서는 이 명령을 거부한다. 마지막 `run.end`는 기록의 완료 표식일 뿐 프로세스 트리 종료 증명이 아니다. 대화 목록과 대화 이벤트 한 줄은 각각 1 MiB로 제한한다. 이 명령은 총괄의 읽기 도구용 페이지와 별도이며 셸이 없는 총괄의 직접 조회 경로가 아니다.

## 비 Windows 시작 전 거부 검토 (미구현)

현재 비 Windows에서는 작업이나 총괄이 정상 종료해도 트리 종료를 증명하지 못해 예약이나 총괄 표식이 남는다. 검증된 격리가 없는 플랫폼을 시작 전에 거부한다면, 공통 실행기에서 최종적으로 차단하고 CLI 직접 분배·총괄 분배·예약 실행과 총괄 메시지의 사용자 진입점에서도 시작 전에 같은 사유를 반환해야 한다. 자식 생성 함수에서만 거부하면 실행 ID와 기록, 자원 예약, 작업 폴더 또는 프로바이더 사전 확인이 이미 생길 수 있고 백그라운드 분배는 처음에 성공처럼 보일 수 있다.

이 방안은 Linux·macOS 등 미지원 플랫폼에서 새 카드와 총괄 실행을 중단하므로 기존 사용 기능의 변경이다. 계획 검사·과거 기록 조회·종료 불명 예약 점검은 실행과 구분해 유지해야 하고, 이미 남은 예약과 표식은 별도 증거 없이 지우지 않는다. Linux의 cgroup v2를 채택하려면 자손의 이탈을 막는 권한 구성, 전체 비어 있음의 확인, 시작·종료·중단·소유자 재시작과 권한 부족을 실제 Linux에서 검증해야 한다. 현재 Windows 개발 환경에는 Linux 실행 환경이 없어 이 대안을 검증하거나 구현했다고 주장하지 않는다.
