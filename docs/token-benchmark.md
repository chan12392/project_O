# 토큰 비교: 기본 하네스 vs 깨끗한 에이전트 + 세션 공유

같은 일을 두 방식으로 시켜 카드당 토큰을 비교한다(ADR-0005).

| 묶음 | 실행 방법 | 카드가 받는 컨텍스트 |
|---|---|---|
| A. 기본 하네스 | `o dispatch --profile own --no-context plan.json` | 각 CLI가 평소 읽는 사용자 하네스(전역 AGENTS·USER·MEMORY, 훅, 스킬, MCP) + 작업카드 |
| B. 깨끗한 + 세션 공유 | `o dispatch --profile project-o plan.json` (기본, `--clean`과 같음) | 작업카드 + 그 일과 관련된 이전 작업 조각(최대 1,500자). 더 필요하면 카드가 `o context`로 찾는다 |

`--profile own`만 준 실행과 `--profile project-o --no-context` 실행도 기록되지만 `--compare`에서는 빠진다(`o tokens`의 모드별 표에는 나온다).

## 준비

1. `o agents doctor`가 깨끗함으로 끝나는지 확인한다(B의 전제). 로그인이 안 됐으면 `o agents login <claude|codex>`.
2. 테스트 프로젝트는 홈 폴더 밖, git 저장소로 둔다. 시작 커밋을 기록한다.
3. 비교할 `plan.json` 하나를 정한다. 카드의 `provider`·`model`·`effort`를 고정한다(빈 칸이면 CLI 기본 모델이 바뀌어 비교가 흔들린다).
4. 세션 공유가 효과를 내려면 그 프로젝트에 이전 실행 기록이 있어야 한다. 실제 쓰는 프로젝트에서 재거나, 먼저 관련 작업 몇 개를 돌려 둔다. `o context "<카드 task의 핵심어>" --project <폴더>`로 무엇이 주입될지 미리 볼 수 있다.

## 순서 (공정하게)

동일한 시작 커밋의 독립 테스트 복사본과 같은 시점의 컨텍스트를 준비한다. 한쪽의 결과가 다른 쪽에 유입되지 않도록 하고 A→B와 B→A 순서를 번갈아 측정한다. 예산에 따라 실제 effort가 달라지거나 한도에 걸린 실행은 그 사실을 기록해 비교에서 구분한다. 비교를 위해 사용자의 예산 설정을 임의로 바꾸지 않는다.

```sh
# 각 복사본에 같은 시작 상태와 계획을 준비한 뒤 실행 ID를 기록한다.
o dispatch --profile project-o C:/bench/plan-b.json
o status <B의 runId>
o dispatch --profile own --no-context C:/bench/plan-a.json
o status <A의 runId>
o tokens --json --since 2026-11-02T09:00:00Z
```

- 한 번으로는 흔들림이 크다. A→B와 B→A를 반복하고 각 실행 ID와 캐시가 따뜻한지 여부를 기록한다.
- 프로바이더의 프롬프트 캐시 때문에 뒤에 돈 쪽의 `캐시 입력`이 유리할 수 있다. 캐시 만료·모델·권한·프로필 변경도 함께 기록하며 구독 환경의 캐시 수명은 가정하지 않는다.
- 같은 PC에서 그 구간에 다른 실행을 돌리지 않는다. 섞이면 `--project`로 걸러진다.
- 실패하거나 사람이 개입한 회차도 기록하고 재시도의 사용량을 함께 센다. 결과 품질(테스트 통과, 바꾼 파일)과 총괄의 사용량도 확인한다 — 토큰이 적어도 일을 못 했으면 의미가 없다.

## 보고서 읽기

아래 표는 보고서 형식을 보여 주는 예시다. 실제로 잰 숫자는 맨 아래 "실측" 절에 있다.

```text
                        기본 하네스         깨끗+세션 공유       차이
실행                              3                  3          -
카드                              9                  9          -
카드당 새 입력               18,400              6,900       -63%
카드당 캐시 입력             41,200             12,800       -69%
카드당 출력                   3,100              2,700       -13%
카드당 합계                  62,700             22,400       -64%
codex 카드당 합계            62,700             22,400       -64%
```

(숫자는 예시다. 실측값이 아니다.)

- **새 입력**: 캐시되지 않은 입력(Claude는 캐시 쓰기 포함). 하네스 크기가 가장 크게 드러나는 줄이다.
- **캐시 입력**: 공급자가 캐시에서 읽었다고 보고한 입력. 구독 한도에 반영되는 비율은 이 수치만으로 알 수 없다.
- **출력**: 생각·답변 토큰(Antigravity는 thinking 포함).
- **합계** = 세 값의 합. 카드 수가 다를 수 있어 카드당 평균으로 비교한다.
- 차이 = (B − A) / A. 음수면 B가 적게 쓴 것이다.
- 토큰을 보고하지 않은 카드(대기 또는 시작 전 실패 포함)와 필드가 빠지거나 불명인 카드는 평균에서 제외한다. 완전성 표식이 없는 과거 기록도 불명으로 표시한다. 완전하게 보고된 값만 요약 합계에 넣고, 선택한 기간에 미보고·불완전 기록이 있으면 전체 캐시 비율은 미측정으로 표시한다.
- 기본 하네스와 깨끗한 프로필·공유 컨텍스트 비교는 두 조건이 함께 바뀐 기술 통계다. 통제된 실험 전에는 차이를 절감 효과로 단정하지 않는다.

다른 보기:

- `o tokens` — 모드별 카드당 평균(프로바이더별 포함)과 실행별·카드별 숫자. `+컨텍스트`는 그 카드에 컨텍스트가 주입됐다는 뜻(`run.context` 이벤트).
- `o tokens --json` — `groups`(모드별), `compare.baseline`/`compare.shared`, `runs`(실행·카드별). 앱 대시보드의 "토큰" 카드도 같은 데이터다.
- 묶음은 실행 폴더의 `clean` 표식(`--profile project-o`)과 카드별 주입 여부로 정한다. 이 기능 이전의 실행은 모두 "주입 없음"으로 잡힌다.

## 카드 프롬프트의 고정 접두부

같은 공급자와 실행 모드의 카드에는 공통 역할·결과·팀 대화 지침을 먼저 두고, 작업명·프로젝트·과제와 실행별 팀 정보는 그 뒤에 둔다. 실행 방식과 동시 작업 여부에 따라 지침은 달라진다. CLI 자체 시스템 프롬프트와 캐시 적용은 공급자가 결정하므로 고정 접두부가 캐시 적중이나 구독 비용 절감을 보장하지 않는다. 위 비교 절차에서 공급자가 실제 보고한 사용량과 누락을 확인한다.

총괄도 고정 역할·계획 지침을 프로젝트 경로와 예산·대화·실행 상태보다 먼저 둔다. 새 세션과 재개 세션, 읽기 전용과 YOLO 모드의 지침은 다르며 실제 캐시 적용 여부는 해당 CLI와 공급자가 결정한다.

총괄 요청 수, 사용량 이벤트가 없는 요청 수, 필드가 빠졌거나 완전성을 확인할 수 없는 사용량 이벤트 수도 따로 표시한다. 진행 중이거나 실행 전에 실패한 요청도 포함된다. 기간 필터는 요청 수에는 요청 시각을, 토큰 합계에는 사용량 이벤트 시각을 적용한다. 공급자가 캐시 필드를 생략하면 실제 캐시 사용량은 알 수 없다.

### 결론

- 이번에 잰 것은 "깨끗한 프로필"의 효과뿐이다. 새 복제본이라 세션 공유 컨텍스트는 한 번도 주입되지 않았고, 문서가 주장하는 "깨끗한 에이전트 + 세션 공유"는 측정되지 않았다. 주입이 일어나지 않으면 `o tokens --compare`는 B를 아예 세지 않는다.
- 같은 일을 끝까지 한 Claude 카드는 B에서 카드당 합계가 31% 적었다(새 입력 -37%, 캐시 입력 -31%, 출력 +5%). 두 회차 모두 같은 방향이었고 결과물 품질(파일 3개, 테스트 통과)도 같았다.
- Codex는 B에서 새 입력이 26% 적었지만 캐시 입력은 26% 많았고, 무엇보다 B의 카드가 읽기 전용 샌드박스 때문에 버그를 고치지 못했다. 이 상태로는 Codex 쪽 절감을 말할 수 없다. 깨끗한 Codex 프로필에서 쓰기가 되게 고친 뒤 다시 재야 한다.
- 전체 카드당 합계 -8%는 Codex B의 실패가 섞인 숫자라 쓰지 않는다. 예시 표의 -64%와 같은 큰 절감은 이번 측정에서 나오지 않았다.
- 한계: 회차당 실행 2개, 카드 8개의 작은 표본이다. 과제가 작아(카드당 20~65초) 하네스 고정 비용 비중이 큰 쪽으로 치우쳤을 수 있다. 실행이 약 2분 간격이라 공급자 프롬프트 캐시가 뒤 실행에 유리했을 수 있다(A의 캐시 입력은 1회차 148,608·170,991, 2회차 123,136·130,828). 모델·effort·계획은 고정했지만 A와 B는 프로필과 컨텍스트 두 조건이 함께 바뀐다.
